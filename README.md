# CaloriQ: Multimodal Nutrition VQA System

CaloriQ is a full-stack nutrition assistant that combines:
- a Flask backend for authentication, image upload, OCR, nutrition parsing, and question answering,
- a Flutter mobile app with camera-first UX, authenticated chat, and persistent chat history,
- optional LLM integration (Qwen via Ollama) for richer, free-form nutrition responses.

This README is the canonical project document for the current workspace state.

## 1. What This Project Does

CaloriQ lets a user:
1. Sign up or log in.
2. Capture a food label image (camera or gallery).
3. Upload the image to the backend.
4. Ask natural language questions about the image (for example: calories, sugar, allergens, healthiness, muscle gain vs fat loss).
5. Receive responses generated by:
   - Qwen (if enabled and reachable), or
   - deterministic rule-based logic (fallback path).
6. Persist chat sessions and replay chat history later.

In short: this is an image-grounded nutrition question answering app with real backend persistence.

Branding note:
- Repository/docs branding is "CaloriQ", while some in-app strings still show "FoodLens" (for example app title/about text). This is a naming transition artifact in the current codebase.

## 2. High-Level Architecture

The repository has two active runtime components:

- `backend/`:
  Flask API + OCR + parsing + QA + persistence.

- `flutter_app/`:
  Mobile app using Riverpod and GoRouter.

Top-level docs:
- `README.md`: this file.
- `steps-to-run`: quick operational runbook for local execution.

### 2.1 Runtime Flow (End to End)

1. Flutter authenticates with `POST /api/auth/register` or `POST /api/auth/login`.
2. Flutter uploads label image to `POST /api/upload-image` as multipart form-data.
3. Backend stores file under `backend/data/images/` and indexes metadata in `image_index.json`.
4. Flutter sends question to `POST /api/ask-question` with `image_id`, `question`, `chat_id`, `language`.
5. Backend pipeline:
   - preprocess image,
   - run OCR (engine priority from environment),
   - parse nutrition fields,
   - answer via Qwen when enabled or rule-based fallback,
   - localize response text,
   - persist user + assistant messages in DB.
6. Flutter renders response and source details in chat.
7. User can revisit sessions via `GET /api/chats` and `GET /api/chats/{chat_id}/messages`.

## 4.4 Route-Level API Contracts

### Authentication (`backend/routes/auth.py`)

1) `POST /api/auth/register`
- Request JSON:
  - `username` (string)
  - `password` (string, min 8)
  - `full_name` (optional)
- Success: `201`
- Response includes:
  - `message`
  - `user` object
  - `access_token`

2) `POST /api/auth/login`
- Request JSON:
  - `username`
  - `password`
- Success: `200`
- Response includes:
  - `message`
  - `user`
  - `access_token`

3) `GET /api/auth/me`
- JWT protected
- Returns current user serialization.

### Upload (`backend/routes/upload.py`)

`POST /api/upload-image`
- JWT protected
- Multipart field required: `image`
- Validates and stores image through `save_uploaded_image()`.
- Success: `201`
- Returns:
  - `message`
  - `image_id`
  - `image` record details

### Question Answering (`backend/routes/qa.py`)

`POST /api/ask-question`
- JWT protected
- Request JSON:
  - `image_id` (required)
  - `question` (required)
  - `chat_id` (optional; generated if missing)
  - `language` (optional; default `en`)
- On analysis success:
  - returns `AnalysisResult` dictionary + `user_id` + `chat_id`.
- On analysis failure:
  - stores fallback assistant message in chat history,
  - returns `422` (`analysis_failed`).

### Chat History (`backend/routes/chat.py`)

1) `GET /api/chats`
- JWT protected
- Lists user chats (latest first).
- Current backend repository implementation applies a fixed server-side cap of 50 chats per request.

2) `GET /api/chats/{chat_id}/messages`
- JWT protected
- Returns messages for chat if it belongs to current user.
- If not found or not owned by user -> `404 chat_not_found`.

### Health (`backend/routes/health.py`)

- `GET /api/health` -> `{status: ok, service: backend}`
- `GET /api/ready` -> `{status: ready}`

## 4.7 OCR Pipeline

Primary implementation:
- `backend/services/ocr_service.py`

Related preprocessing:
- `backend/services/preprocessing_service.py`

Engine support:
- `easyocr`
- `pytesseract`
- `paddleocr`
- `auto` mode

Engine selection logic:
- Controlled by `OCR_PRIMARY_ENGINE`.
- If `auto`: order is `paddleocr`, `easyocr`, `pytesseract`.
- Otherwise: requested engine first, then remaining engines as fallback.

OCR reliability behaviors:
- lazy imports for heavy OCR libs,
- reader instances cached (`lru_cache`),
- robust fallback if one engine fails,
- error accumulation when all engines fail.

Text cleanup:
- strips control chars,
- normalizes whitespace,
- removes noisy characters while preserving common nutrition symbols.

Preprocessing steps:
1. Resolve uploaded image by `image_id`.
2. Decode image bytes through OpenCV.
3. Resize with aspect ratio cap (default 1600x1600).
4. Convert to grayscale.
5. Denoise (`fastNlMeansDenoising`).
6. Write processed file next to original (`*_processed`).

## 4.8 Nutrition Extraction and QA Logic

Files:
- `backend/services/nutrition_parser.py`
- `backend/services/advanced_inference.py`
- `backend/services/qa_engine.py`
- `backend/services/analysis_service.py`

### Nutrition extraction

- `NutritionExtractor` uses regex patterns to parse:
  - calories,
  - protein,
  - fat,
  - carbs,
  - sodium,
  - fiber,
  - sugar.
- Unavailable fields are represented as `Not found` at extractor stage.
- Parser converts to typed numeric values or `None` in `NutritionProfile`.
- Ingredients extracted heuristically from OCR text sections.

### QA strategy

`answer_question()` in `qa_engine.py` follows this sequence:
1. Normalize and validate question.
2. Compute health analysis and diet recommendation context.
3. If `ENABLE_QWEN=true`, attempt Qwen answer via Ollama.
4. If Qwen unavailable/fails, use deterministic intent logic.

Supported intent categories include:
- calories,
- sugar,
- fat,
- protein,
- healthiness,
- allergens,
- ingredients,
- fitness-goal comparison (muscle gain vs fat loss),
- generic fallback.

Confidence:
- derived from available nutrition-field coverage and quality of answer path,
- capped and reduced for non-committal fallback answers.

### Analysis orchestrator

`AnalysisService.analyze()` does:
1. language normalization,
2. OCR extraction,
3. nutrition parsing,
4. VLM placeholder hook (currently disabled unless future integration enabled),
5. QA response generation,
6. i18n translation pass,
7. output assembly to `AnalysisResult`.

Failure handling:
- OCR/parser/QA exceptions become `AnalysisServiceError` with user-facing message.
- Empty OCR text path gives a specific retake-photo instruction.

## 4.10 Persistence Layer

Files:
- `backend/services/database.py`
- `backend/services/db_models.py`
- `backend/services/repositories.py`
- `backend/services/legacy_migration.py`

Database:
- SQLAlchemy 2.x.
- Default DB URL: SQLite file at `backend/data/caloriq.db`.
- Enables SQLite foreign keys via PRAGMA.

ORM entities:
- `users`
- `chat_sessions`
- `chat_messages`

Chat persistence behavior:
- each ask-question call saves:
  - one user message,
  - one assistant message,
  in a chat session keyed by `chat_id`.
- chat session `updated_at` is refreshed on each exchange.

Legacy migration:
- if DB users table empty and `users.json` has entries,
- imports legacy users once,
- avoids duplicates by id/username checks.

## 12. Known Limitations and Practical Risks

1. OCR variability:
- blurry, skewed, or low-light labels can fail extraction.

2. i18n is phrase-map based:
- not full semantic translation; only mapped fragments are translated.

3. Health scoring is heuristic:
- useful guidance but not medical-grade diagnostics.

4. Local persistence model:
- SQLite + local files are sufficient for local/dev, but not production hardened.

5. Some Flutter legacy code remains:
- older mock chat/provider files coexist with current architecture.

6. Release signing:
- Android release build in repo still points to debug signing placeholder.

## 14. Quick Troubleshooting Matrix

Issue: `POST /api/ask-question` returns 422
- Cause: OCR or parse failure.
- Action: retake clearer nutrition-label image with good lighting and framing.

Issue: mobile app cannot reach backend
- Cause: IP, firewall, or wrong API base URL.
- Action:
  - verify backend running,
  - verify same network,
  - allow TCP 5000,
  - check app Settings URL,
  - for USB use `adb reverse`.
  - if auto-discovery cannot find backend, save the URL manually in Settings.

Issue: Qwen responses missing or generic fallback used
- Cause: Ollama not running or model unavailable/timeout.
- Action:
  - start Ollama,
  - verify model pull,
  - increase `QWEN_TIMEOUT_SEC`.

Issue: dependency install failures around numpy/opencv stack
- Cause: Python/toolchain mismatch on local environment.
- Action:
  - use Python 3.11/3.12 virtual env,
  - update pip/setuptools/wheel,
  - reinstall requirements.
